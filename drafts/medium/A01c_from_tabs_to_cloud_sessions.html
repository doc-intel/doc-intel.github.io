A New Way of Working with Claude

Running Claude Code in Parallel: Tabs, Subagents and Cloud Sessions

The ways I put Claude Code to work, from one tab to a fleet of cloud sessions, what each one is good for, where it stops, and the tips I wish I had known earlier

Claude Code can work in several ways: one session in your editor, several tabs side by side, subagents inside a session, and sessions in the cloud that keep going when your PC is off. Each one fits a different kind of work, and I have found that most of my bad days came from using the right tool at the wrong size. In this article, I'd like to share each way, what I use it for, where it stops, and the small habits that made it work.

For context, I build a large web application mostly on my own, with Claude Code writing most of the code. Over a few months I went through all of these, roughly in the order below, and each step fixed the worst problem of the one before. The lesson I took from the whole journey fits in one line, and I will come back to it: launching a session is cheap, but merging its work is not.

The ways covered in this article, from the smallest to the largest

1. One session in one tab

This is where everyone starts, and for many tasks it is still the right choice. You describe the task, Claude reads the code, proposes a change and runs it. If the work fits in your head, say, fixing an export or adding one field to a form, a second session would only add the cost of explaining the split.

Three habits made my single sessions much better. First, for anything that touches more than a few files, I start in plan mode (Shift+Tab in the terminal) and read the plan before any code is written. Correcting a plan takes a minute, and correcting a finished diff can take an hour. Second, I type /clear between unrelated tasks, because everything read for the previous task stays in the context and is sent again with every request. Third, I always give Claude a way to check its own work: the test command, the script that should return zero, or the screen to capture. A session that can run a check stops when the check passes, not when the code looks done.

The limit of one session is simply that you wait. While it works, you watch, and that is what pushes most of us to open a second tab.

2. Several tabs side by side

In VS Code, each Claude Code session is a tab with its own conversation, working in the same repository. Five independent tasks, five tabs. Up to a handful, this works well, and it is the cheapest way to get parallel work.

Beyond that, two things go wrong. You become the scheduler: each new task costs a click, a prompt and some of your attention, so your day goes into handing out work instead of judging it. And everything runs on your PC. Each session starts its own Python server, its own test run, its own headless browser for screenshots. On 8 November I had twenty tabs open, each doing a reasonable job, and twenty of each was more than 32 GB of RAM could hold. My PC froze, I restarted it, and an hour later it froze again.

Twenty sessions, twenty sets of servers and browsers, one PC

If you work with tabs, a few rules help a lot:

  1. One subject per tab. Two tabs on the same screen will each be right on their own and conflict when you merge.
  2. One heavy job at a time. A server, a full test run or a browser is heavy; let one tab run it while the others read and write code. I now run a small script that checks free memory before anything heavy starts, and it waits when the machine is busy.
  3. Leave nothing running. Ask each session to stop its servers and close its browser when it is done. Most of my lost RAM was processes nobody needed anymore.
  4. Give tabs their own working copy when they write a lot. A git worktree per tab means two sessions never edit the same file on disk at the same moment.

3. Subagents inside one session

A subagent is a helper that one session starts for a piece of its own task, with a fresh context. I use them for three things. One is searching a large codebase without filling the main conversation with every file read. Another is a lot of mechanical work, say, checking two hundred screenshots. The third is a second reading of a change by a reviewer that did not write it.

When you hand work to a reviewer subagent, give it the code and the requirement, not your conclusion. In my experience a reviewer told "this looks fine, can you confirm?" tends to agree, while one given only the diff and the ticket finds real faults. You can also give each subagent its own model with the model: field. A lighter model is usually enough for sorting, counting and listing. When I compared my own sessions over a few days, the strongest model cost about twice as much per session, and for routine work nothing showed that it did better.

The agent map shows what runs inside a session: the subagents it started and the background tasks it left running. I hoped it would show all my tabs. It does not, but it is where I found a server that had been running for two hours, and stopped it.

The agent map shows one session from the inside. The other nineteen tabs are not on it

The limit is that a subagent lives inside its session, on the same machine. It cannot own a task, it does not get its own branch, and it does not help with RAM. It is a way to keep one session focused, not a way to run more sessions.

4. Cloud sessions

Cloud sessions moved the work off my PC. You open Claude Code on the web (claude.ai/code), pick a repository and describe a task. Claude gets its own cloud machine and a fresh clone, works on its own branch, and keeps going when your laptop is closed. When it finishes, you get a branch to review and merge.

This is where long and heavy work belongs: a feature across several modules, a full rebuild of a docs site, a long series of screenshots. My PC stayed quiet from the first afternoon.

Two habits matter more here than in a tab, because you are not watching. Write the task as a file in the repository, not only as a chat message: a short ticket in Markdown with your exact words, the date and what "done" means. I keep tickets in one folder per state (open, in progress, closed), so every session can read them and git records every move. And ask each session to end on one line, "ready to merge" and its branch name, with everything else written in the ticket. When many sessions report at once, a single final line makes the ones with a question easy to find.

A cloud machine has your repository, but not your environment. I still keep a few local tabs for work that needs tools installed only on my PC, for confidential data that must not leave my disk, and for looking at the app at my real screen size. They follow the same rules as everything else, one heavy job at a time.

5. One session that launches the others

What changed my days most is that a cloud session can launch other cloud sessions through its session tools (not every account has them yet, so check yours first). I keep one coordinating session open. I tell it what I want, and it writes the ticket, launches a worker session for it, and later reviews and merges the result. I talk to one session instead of watching many.

One coordination session, five workers, two reviewers. Each worker has its own branch

On the first afternoon the coordinating session launched fifteen workers, and main started moving fast: 394 merges in the week of 2 November, 678 the week after. For a week, the problem looked solved. Then I cleaned up the repository's branches, measuring for each one how far it was ahead of main and how much of its work had already reached main.

38 branches. Most could go. Six held real work that had never reached main

Of 38 branches, 27 could simply be deleted and 4 were still in progress. Six held real code that had never reached main, and one of them had 38 conflicts by the time anyone looked. The last one held a fix that main needed, reviewed and approved, which had waited four days because the coordinator was busy launching new sessions. The merge count had hidden all of this: a hundred merges a day tells you the easy branches flow, and nothing about the hard ones waiting in the queue.

No session had failed; the cost had moved. Launching a session is one tool call. Merging its branch safely means fetching it, checking it against main, reading the diff, running the app, comparing the result with the ticket and sometimes resolving conflicts line by line. That is a queue, and Little's law applies to it: the average wait of a branch is the number of branches waiting divided by the number merged per day. Adding workers raises the arrivals, and only reviewers raise the departures. The reviewer is also the expensive seat. On a recent day a worker session cost 7 to 35 dollars and a reviewer close to 60, because a review reads far more than it writes.

On your PC the limit is your attention and your RAM; in the cloud it moves to the reviewers

The same picture exists as a scene you can turn around, where the queue of branches grows and drains: the 3D version on doc-intel.github.io.

Workers write, reviewers check, only the coordination merges. The reviewers set the pace

Here is what I do now, each point an answer to something that went wrong:

  1. Size the fleet by the reviewers. We started at fifteen workers; about six is what two reviewers could keep up with. When branches wait for review, add a reviewer, not a worker. A third reviewer raised our throughput more than an extra worker would have, because it worked on the part that was stuck.
  2. Send every request through one door. The coordinating session writes the ticket with your exact words and the date, gives it a number, then launches a worker. No request reaches two sessions.
  3. Protect main. Only the coordinating session merges, local tabs included. A written rule was not enough: a session started outside the coordination pushed straight to main, and that cost an hour and 14 conflicts. Branch protection on main, which requires a pull request, is what held.
  4. Claim the ticket before writing code. A session moves its ticket to in_progress/ and pushes that move before its first line of code, so every other session sees that it is taken.
  5. Merge small, the same day. A branch should live hours, not days. Merge the exact commit that was reviewed, so that a late push cannot slip in. And check each branch cheaply before anyone reads it:
git fetch origin
git rev-list --left-right --count origin/main...origin/my-branch   # behind, ahead
git merge-tree --write-tree origin/main origin/my-branch > /dev/null || echo "conflicts"
  1. Run a closing script before "ready to merge". About half our round trips were chores, not faults: a ticket not moved to closed, a number already taken. A script catches those, so reviewers spend their time on real problems, like the pages broken by a new logo, the work queue that shrank from 449 items to 7, or the page that said "no LLM" for a tool that calls one. When a fault is caught twice, it becomes an automatic check.

Which one to pick

If I had to start again, I would use one session for anything I can describe in a few sentences, and add subagents when that session needs to search widely or get a second reading. I would open more tabs only for independent tasks that are light on my machine, and send anything long or heavy to the cloud. The coordinating session comes last, once I have a ticket folder, branch protection on main and at least one reviewer. Since launching is cheap and merging is not, the number to watch at every stage is how long a finished branch waits before it reaches main. I now track it, with the number of round trips per branch, and when either one grows I add review capacity, not workers.

If you want to try the fleet without the trouble I had, a small start works well. Open one coordinating session with a tickets folder, and let it launch two or three workers, with one ticket and one branch each. Add one reviewer that sees only the branch and the ticket, and merge every reviewed branch the same day. Add a worker only when no branch is waiting for review. I would be glad to hear which of these ways works best for your own projects, and what breaks first when you scale it.
